# 系統怎麼加入 LLM：討論稿（2026-11-24）

> 假設你說的「ll」是 **LLM**（大型語言模型）。如果不是，告訴我再改。
> 依你 11/10 的決定：**語音／VLA 只當支線或未來工作，主線（MCU 上的短校正＋事後標籤＋跨配戴累積）先做完**。下面的規劃照這個原則，LLM 不能進入自我測試和正式實驗的流程，除非你和老師另外決定，而且要在報告裡寫清楚。

## 1. 原則：LLM 放在哪一層

| 層 | 週期 | 誰負責 | LLM 可以嗎 |
|---|---|---|---|
| 肌電 → 指令（STM32） | 100 ms | LDA＋決策（確定性） | **不行**：延遲、不確定性、無法驗證 |
| 安全（deadman、停止、工作空間、急停） | 100 ms | 確定性程式碼 | **絕對不行** |
| 輔助控制（雙模式、目標機率 P(g)） | 100 ms | `modes.py` | 不直接控制；**可以提供先驗** |
| 任務層（要拿哪個、放哪裡、順序） | 秒級 | 目前是使用者自己 | **可以**：這是 LLM 最適合的位置 |
| 人機溝通（說明、提示、紀錄） | 秒級 | 目前是固定字串 | **可以** |

**一句話**：LLM 只能**建議目標**，不能**產生速度**。它的輸出一律要先經過確定性的檢查，才會影響手臂；這些檢查包括物體 ID 是否存在、架子是否有空位、是否在工作空間內。

## 2. 具體可以做的四件事（依價值和風險排序）

### A. 語音或場景提供「目標先驗」給輔助控制（最推薦）
- 現在 `modes.py` 的 `mix` 規則，是依 P(g)（每個物體是目標的機率）調整輔助方向；P(g) 只從手臂的運動推論。
- 加入：使用者說「拿藍色杯子」→ 語音轉文字（本機）→ 小型 LLM，或規則加詞表，把話對應到場景中的物體 ID → 給 P(g) 一個先驗。
- **預期效果**：鎖錯目標變少、接近更快。35.83 的閉迴路模擬裡，鎖錯是主要的失敗型態。
- **怎麼先驗證，不必碰硬體**：在 `closed_loop_fw.py` 或 `modes_sim_emg.py` 裡模擬先驗的品質（正確率 p，錯的時候指向別的物體），量鎖錯和時間隨 p 的變化。這可以先做，而且數字可以進論文的「未來工作」或附錄。
- **安全**：先驗只改 P(g)；手臂的移動仍然只來自 EMG 指令，deadman、工作空間、停止都不變。先驗錯了，最壞的情況是輔助方向偏了，使用者可以用 EMG 修正（35.67 的「輸入不符就退出」）。

### B. 任務規劃（多步驟）
- 例如「把三個杯子都放到上層」→ LLM 拆成（拿 0 → 放 4）、（拿 1 → 放 3）……
- 系統依序把目標先驗設好，使用者仍然用 EMG 完成每一步；計畫的每一步都要檢查可行性（物體存在、架子有空位）。
- 價值在「減少使用者的認知負擔」，但評估要有多步驟的任務設計，屬於比較後面的工作。

### C. 自然語言說明（低風險、低成本）
- 手臂停下時，告訴使用者原因：「沒有心跳，已停止」「到達工作空間邊界」「放置位置太靠近邊緣」。
- 現在 `modes.py` 已經有固定的中文提示（`hint_zh`），LLM 只是把它說得更自然。**不需要 LLM 也能做**，所以優先度低。

### D. 離線分析助手
- 讀每次實驗的紀錄（`mcu.csv`、`task.csv`、`board_events.csv`），自動摘要異常：哪一段誤觸發多、哪個手勢常錯、標籤錯誤率。
- 完全不碰即時控制，風險最低。可以當研究工具，不算系統的功能。

## 3. 硬體可不可行（你的筆電：RTX 3060 Laptop 6 GB）

- 已經量過（11/09，SmolVLA）：VLA 的推論峰值約 1.2 GB，每次 0.5–0.8 s。
- 語音：Vosk（限定詞彙，CPU）或 Whisper-small（GPU 可以）都夠快。
- LLM：3–4B 的模型量化到 4-bit 可以放進 6 GB（勉強）；7B 放不下。**A 用不到大模型**：「拿藍色杯子」對應到物體 ID，用詞表加小模型或規則就夠了。
- 延遲：目標層是秒級，0.5–2 s 可以接受。即時層（100 ms）不受影響，因為 LLM 不在這條路上。
- **不要用雲端 API 控制手臂**：網路斷掉時不能讓手臂的狀態不確定；而且實驗資料不應該外送。

## 4. 架構上怎麼接（不動韌體）

```
麥克風 ─► 語音轉文字 ─► 目標解析（詞表 / 小 LLM）─► 檢查（物體存在？）─► prior,<p0>,<p1>,<p2>
                                                                            │（TCP，同一條 relay 通道）
板子 ─► 橋接程式 ─► udp_tcp_relay ─► assist_ros.py board ◄─────────────────────┘
                                         │ P(g) ← 運動推論 × 先驗
                                         ▼
                                   modes.py（雙模式、輔助）─► guard() ─► 手臂
```

- `assist_ros.py` 只要多接一種訊息 `prior,...`，乘到 P(g) 上。
- 先驗設定有效期限（例如 30 s），而且放下物體後就清掉。

## 5. 對論文的定位

- **主線不變**：MCU 上的短校正、活動量門檻、事後標籤、跨配戴累積、Kinova 實機閉迴路。
- LLM 最多出現在：
  1. 未來工作的一段；
  2. 或一個獨立的模擬附錄：「語音目標先驗對雙模式輔助的影響」，用 35.83 的閉迴路模擬量化。
- 如果要做成實機 demo，要在主線實驗**之後**、另外標明，不能混進受試者流程（11/10 的決定）。
- 對求職（科技業、智慧製造）的價值：「確定性的即時控制＋LLM 只在監督層」，這個分層正是工業上要的，可以寫成架構的亮點。

## 5.5 模擬結果（2026-11-24 已做，report 35.86–35.87）

- 用真的韌體和你自己錄的 EMG 跑閉迴路模擬。先驗接法：
  - P(g) × 先驗；
  - 先驗 < 0.2 的物體要停滿 1 s 才鎖定，使用者可以靠停久一點覆蓋 LLM。
- **3 個物體、分得很開的場景**：沒有可量測的好處，因為從運動就猜得很準。
- **擁擠場景**（6 個物體，兩兩相距 8 cm）：
  - 「停 1 s 才鎖」**本身**（不需要 LLM）就減少大部分的鎖錯，但每次取放多 2–4 s；
  - **準確的先驗（p 0.95）**保住鎖錯的減少，又把時間拿回來；最難的一組少 1.19 次／次（35.88，15 輪配對）。
  - **35.88 更正**：先驗只有 50 % 準時，鎖錯也會減少，時間只多 1–2 s。「≥ 80 % 才值得接」這個門檻撤回，改成「越準越好」。
- **35.88**：鎖錯有 85–95 % 是**放錯架子**，不是拿錯物體。
  - 「只有擁擠的物體要停」（依情境停留）沒有效果。
  - 有效的是**放置時的停留**，代價是每次多 2–4 s。
  - 所以 LLM 先驗最有價值的地方，是告訴系統「**放到哪裡**」。
- **35.89**：不用 LLM，改用「搬運動作的意圖信心」，也能拿到大部分的好處。
  - 規則：P(架子) ≥ 0.8 才停下就鎖，其他要停 1 s；沒有空位的架子不鎖。
  - 鎖錯的減少接近「每次都停」，時間沒有可量測的增加。
  - LLM 先驗的額外價值，只剩最難的那一組，所以更確定是未來工作。

## 6. 建議的下一步（如果你要做）

1. 先做 A 的**模擬**：在閉迴路模擬裡加入先驗，正確率 p 取 0.5／0.8／0.95，看鎖錯和時間的變化。大約半天，不用新硬體。
2. 結果有意義，再決定要不要做語音的實機部分（Vosk 限定詞彙，CPU 就能跑）。
3. LLM 本身最後才加，而且只用在「話 → 物體 ID」這一步。
